  1. What is the difference between a working directory, the staging area, a commit, and a remote repository?

The working directory is the files on disk that I edit. The staging area is where I put the specific changes I want in my next commit, so I can commit some edits and hold others back. A commit is a permanent snapshot of what was staged, stored in my local history; the remote repository is the copy on GitHub, which sees none of it until I push.

2. What do <tt>HEAD</tt>, <tt>main</tt>, and <tt>origin</tt> refer to in a normal repository?

HEAD points to where I am now — normally the checked-out branch, which is why new commits extend it. main is a branch, just a moving pointer to the latest commit on that line. origin is the name of the remote I cloned from, so origin/main is my local record of where main was on GitHub as of my last fetch.

3. Why should you pull or fetch recent <tt>main</tt> changes before starting new work?

So I build on what has already landed instead of a stale copy. The longer I work from an old main, the further my branch drifts and the uglier the eventual merge gets. Pulling first also surfaces conflicting work early, when it is cheap to fix.

4. What is the difference between fetching and pulling?

Fetching downloads new commits and updates remote-tracking branches like origin/main, without touching my branch or my files. Pulling is a fetch plus an immediate merge (or rebase), which does move my branch and change my working directory. Fetching is always safe; pulling actually modifies my work.

5. What is the difference between merging and rebasing? When is rebasing a shared branch dangerous?

Merging joins two histories with a new commit that has both as parents, preserving what actually happened. Rebasing replays my commits on top of another branch for a linear history, but the replayed commits are new objects with new hashes. That makes rebasing a shared branch dangerous: it needs a force-push, which can overwrite teammates' work and leaves anyone holding the old commits with a diverged branch.

6. Why are pull requests useful even though they are not part of Git itself?

Git can merge branches but has no opinion on whether a merge should happen. A pull request adds that layer — review, line comments, automated checks — before anything reaches main, and it records why the change was made. It also gives CI a gate, since the merge button can be blocked until the build passes.

7. In Task 4, Git created a new commit called ‘Merge branch 'can’`. Why was a new commit needed?

main and can had both moved on from their shared ancestor, and neither was an ancestor of the other. A fast-forward only works when the target branch is strictly ahead, which main was not. So Git had to create a commit with two parents to record that the two lines were joined.

8. In Task 5, both branches changed <tt>src/main.cpp</tt>. Why did <tt>can_id</tt> merge by itself but <tt>@version</tt> and <tt>loop()</tt> did not?

Git compares each side against the merge base, not against each other. can_id was 0x123 at the base and only main changed it, so there was one unambiguous change to apply. But @version went from 1.1 to 1.1.1 on slow-blink and 1.2.0 on main, and the delays went from 1000 to 500 and 100 — two competing edits to the same lines, which Git has no basis to choose between.

9. In Task 6, which workflow ran when you pushed to <tt>ci</tt>, and which did not? Why? What does the CI workflow protect the team from?

PlatformIO CI ran, since its trigger is on: [push] — any branch. Doxygen GitHub Pages Deploy Action did not, because it is scoped to pushes to main; it only fired after the PR merged. That is deliberate: check the build everywhere, but publish docs only from main. CI protects the team from broken code reaching main, by compiling every push on a clean machine instead of trusting my laptop.

10. What does a <tt>.gitignore</tt> file do, and why does it not remove a file that was already committed? Why is <tt>.pio</tt> in <tt>.gitignore</tt>?

.gitignore lists patterns Git should not pick up as untracked files, keeping generated junk out of git status. It only applies to files Git is not already tracking — once a file is in the index, a later ignore rule does not revoke that, and it stays tracked until removed with git rm --cached. .pio is PlatformIO's build directory: large, machine-specific, and fully regenerated by pio run, so committing it would bloat the repo for nothing.
